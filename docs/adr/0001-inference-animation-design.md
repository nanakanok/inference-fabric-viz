# ADR 0001: 推論動作アニメーション Web ページの設計

- Status: Accepted
- Date: 2026-10-31（同日、Codex による敵対的レビューを受けて §5・7・8・12・13・15 などを改訂し、§17〜19 を追加。さらに既存の調査資料（DeepEP の動作モード、KV の層ごとの転送、異種チップによる AFD など）との照合で §7・12・17 を修正し、§20 を追加。Codex の再レビューを受けて §7・8・12・13・15・17・18・19 を修正）

## Context

LLM 推論（MoE モデル）の動作を、Web UI 上のアニメーションで分かりやすく説明するページを作る。対象は次の 3 軸。

- 推論構成: PD 分離（Prefill / Decode）と AF 分離（Attention / FFN）
- ネットワーク: Scale-up（ノード内 NVLink）と Scale-out（Leaf-Spine）
- Scale-out の配線: レール最適化あり / なし

比較軸が多いため、何を見せて何を見せないかを先に固定しないと、画面も実装も散らかる。以下はインタビュー（grill-me）で決めた内容である。

初版に対する Codex のレビューでは、次の点が指摘された。A↔F を M:N としながら同じ番号の GPU 同士に揃えていた矛盾、KV の対応が KV の持ち方から導かれていなかったこと、PXN を通信の種類として扱っていたこと、AF の演算の担当が未定だったこと、DP attention と「1 リクエストが全 GPU を流れる」描写の矛盾である。いずれも追加の質疑で設計判断を行い、本版に反映した。

## Decisions

### 1. 想定利用者: 説明者が操作しながら話す技術説明用

技術説明の場で、説明者がステップ送り・一時停止・構成切り替えをしながら話す使い方を主とする。展示向けに自動再生モードも付ける。

- 理由: 比較軸が多く、説明者が切り替えて見比べる使い方が最も効く。
- 定量シミュレータ（パラメータを変えると性能が変わるもの）にはしない。正しい数値モデルの構築コストが大きく、目的（仕組みの理解）から外れる。

### 2. アニメーションの粒度: リクエストの流れ＋集団通信パターン

リクエストの流れ（到着 → Prefill → KV 転送 → Decode → トークン出力）に加えて、通信パターンを描き分ける。

- MoE の EP による dispatch / combine（ノード内 NVLink とノード間 Scale-out の両方）
- PD 間の KV Cache 転送（1 対 1）
- AF 間の activation 送信（A→F）と結果の返送（F→A）。M:N 通信（§17）
- GPU 内部の処理は、代表 GPU のカードとしてトポロジの下に描く（§22）。トポロジ上の 32 GPU には内部を描かない。各フェーズでは代表の 1 層を描き、全層を順に処理していることを常に表示する（§7）。
- 理由: AF 分離とレール最適化の差は、どの GPU がどのスイッチを通って通信するかを描かないと伝わらない。レイヤーまで描くとネットワークの話がぼやける。

### 3. 構成モード: PD 分離 × AF 分離の独立した 2 トグル（MoE 前提）

| PD | AF | 構成 |
| :--- | :--- | :--- |
| OFF | OFF | 統合型（基準） |
| ON | OFF | PD 分離 |
| OFF | ON | AF 分離（Prefill と Decode の両方を A / F に分けて処理する） |
| ON | ON | PD＋AF（Decode 側だけを A / F に分ける） |

- 理由: 2 トグルにすると「PD 分離はフェーズ間で KV を移す」「AF 分離はレイヤー内で activation を往復させる」という、両者が独立した軸であることが UI で自然に伝わる。
- MegaScale-Infer や Step-3 の AFD は参考にした方式であり、それらを再現するものではない。演算の担当の境界は §17 で独自に定める。
- モデルは MoE（DeepSeek-V3 相当）を前提とし、Dense モデルは扱わない。AF 分離の意義も EP の通信も MoE 前提の話であるため。

### 4. 物理トポロジ: 8 GPU HGX 型 × 4 ノード、Leaf-Spine

- 1 ノード = 8 GPU + Scale-up Switch（Scale-up）。製品名を避け、NVSwitch・UALink Switch・SUE（Scale-Up Ethernet）のスイッチなどを総称して「Scale-up Switch」と表記する。同様に、画面と README では NVLink を「Scale-up リンク」、NVLink 中継を「Scale-up 中継」と表記する。本 ADR では、DeepEP や NCCL PXN の実装を説明する文脈に限って NVLink の語を残す（NVIDIA の環境での実際の経路であるため）。各 GPU に Scale-out 用 NIC を 1 枚ずつ（8 レール）。
- 表示規模: 4 ノード × 8 GPU = 32 GPU、Spine 4 台。
- レール最適化あり: Leaf 8 台。各ノードの GPU i の NIC は Leaf i に接続。
- レール最適化なし: ToR 型。Leaf 4 台で、ノード n の 8 NIC はすべて Leaf n に接続。
- リンク容量と比較条件は §18 で定める。
- NVL72 型（ラックスケール）は扱わない。必要なら「Scale-up を大きくすると Scale-out に出る通信が減る」という補足にとどめる。
- GPU の世代は特定しない（§19）。
- 理由: レール有無の違いが最もはっきり見えるのが 8 レール構成。NVL72 ではレールの概念が薄れ、画面も埋まる。

### 5. 並列化とノードへの役割割り当て

**Attention は TP=1 の DP（DP attention）とし、1 GPU が 1 つの replica を担う。** 1 つのリクエストの Attention と KV Cache は、ある 1 GPU が担当する。MoE 層では、routed experts を EP で分散して配置する。

| モード | Attention（DP） | routed experts（EP） |
| :--- | :--- | :--- |
| 統合型 | 全 32 GPU（DP=32） | 全 32 GPU（EP=32、1 GPU あたり 8 Expert） |
| PD 分離 | Prefill: ノード 0-1（DP=16）／Decode: ノード 2-3（DP=16） | 各側の 16 GPU（EP=16、1 GPU あたり 16 Expert） |
| AF 分離 | ノード 0-1（DP=16） | ノード 2-3（EP=16） |
| PD＋AF | Prefill: ノード 0-1（DP=16、Expert も同じ GPU 群で EP=16）／Decode-A: ノード 2（DP=8） | Decode-F: ノード 3（EP=8、1 GPU あたり 32 Expert） |

- **KV 転送**は、Prefill を担当した GPU から、スケジューラが選んだ Decode（または Decode-A）の GPU への 1 対 1 とする。GPU i → GPU i（同じレール）は**スケジューラの選択の一例**であり、仕様として固定しない。レール最適化を意識して配置すれば同じレールを選べ、Leaf 1 台で済む。別のレールを選べば Spine を通る。PD＋AF のように Prefill 16 GPU → Decode-A 8 GPU となる場合も、どの Decode GPU に割り当てるかの話になるだけで、対応関係は破綻しない。
- 画面上には、どのレールが選ばれたかと、その結果のスイッチ通過数を表示する。
- 理由: TP を使うと MLA の圧縮 KV（latent）が TP の各 rank に重複して置かれ、KV 転送の説明が複雑になる。DP attention なら KV 転送は 1 対 1 となり、レールを意識した配置の効果もそのまま見せられる。SGLang などが DeepSeek 系で採用している構成でもある。
- DeepSeek-V3 の技術報告にある実運用の配置（Prefill は Attention TP4 × DP8・EP32、Decode は TP4 × DP80・EP320）とは異なる、縮小した模式配置であることを明記する。

### 6. 実装技術: Vite + TypeScript + SVG（フレームワークなし）、データ駆動

処理を次の 4 層に分ける。

1. トポロジ定義（ノード・GPU・NIC・Leaf・Spine・リンク）をデータで持つ
2. モード（PD / AF）、レール有無、Decode の NVLink 中継の有無から経路を計算する（§12・13）
3. ステップ列（どのフェーズで、どのフローが、どの経路を流れるか）を生成する
4. SVG 上で粒を動かして描画する

- 配布: `vite build` の静的ファイルに加え、`vite-plugin-singlefile` で単一 HTML も出力する（オフラインの展示 PC でも開けるように）。
- 理由: 状態の組み合わせ（2 トグル × レール有無 × ステップ）が多く、型で層を分けないとコードが絡まる。React は UI 部品にしか効かず、アニメーション本体は SVG を直接扱うことになるため使わない。

### 7. ステップの切り方と同時に流す量

**流れる単位**: どちらのモードでも、バッチ（各 Attention GPU に 1 リクエスト程度）を流す。そのうちの 1 リクエストを強調色で追跡し、他のリクエストは淡い色で描く。これにより、1 本を追う説明と、MoE の通信が全 GPU に広がる様子を両立させる（DP attention では、1 リクエストの Attention と KV は 1 GPU が担当するため）。

**比較用ワークロードの固定**: リクエスト（プロンプトとトークン数）、各トークンの router の選択（top-8 の Expert と重み）、Attention GPU への割り当て、Decode 先の選択は、プロンプトと固定のシード値から決定的に生成する。レール有無と「Decode も NVLink 中継する」の切り替えでは、これらをすべて保持し、経路だけが変わるようにする（経路の差とワークロードの差を混ぜないため）。PD / AF の切り替えでは GPU の役割が変わるため、割り当ては作り直すが、リクエストと Expert の選択は保持する。Decode 先の割り当て規則（例: PD＋AF で Prefill 16 GPU → Decode-A 8 GPU）は、同じレールを優先し、負荷が均等になるように選ぶ。

ステップ列（PD＋AF の場合）:

| # | ステップ | 補足 |
| :--- | :--- | :--- |
| 1 | バッチ到着、スケジューラが Prefill GPU に割り当て | 追跡するリクエストを強調する |
| 2 | Prefill: 先頭 3 層（dense） | ノード内の処理のみで、通信は発生しない。早送りで表示 |
| 3 | Prefill: MoE 層（代表 1 層）。Attention → router → dispatch → routed experts ＋ shared expert → combine | 「代表 1 層を表示中（MoE 層は 58 層あり、順に処理）」を常に表示する |
| 4 | Prefill: 全 61 層の完了 → 出力 head → 最初のトークンを生成 | 最初のトークンが Prefill から出ることを明示する |
| 5 | 予約済みの Decode-A GPU へ KV 転送（direct） | 同じレールが選ばれたか、別のレールかを表示する。説明文に「実際は層ごとに送り、Prefill の計算と重ねる」と書く |
| 6 | Decode: 直前のトークンを入力として Attention → router | |
| 7 | Decode: A→F（Expert を持つ F GPU へ直接、direct RDMA） | レールをまたぐ送信はレール最適化ありでも Spine を通る |
| 8 | Decode: routed experts → F→A → 合算 ＋ residual（代表 1 層） | |
| 9 | Decode: 全層の完了 → 出力 head → 次のトークン | 6〜9 を 2〜3 回描いた後「以下繰り返し」と表示 |

他のモードでは次のように省略・置換する。

- PD 分離なし: ステップ 5 の KV 転送はなく、同じ GPU がそのまま Decode に入る。
- AF 分離なし: A→F / F→A は、同じ GPU 群での EP の dispatch / combine に置き換わる。
- PD 分離なし ＋ AF 分離あり: Prefill の MoE 層も A→F / F→A で処理する。

モードごとの見せ方:

- 説明（ステップ送り）モード: 1 つのバッチを上記のステップで追う。
- 自動再生モード: 複数のバッチを重ねて流す。PD 分離で Prefill と Decode が並行して動く様子、AF 分離のマイクロバッチのピンポン（マイクロバッチ数 = 2）を見せる。

KV 転送のタイミング:

- Decode 先は、最初の KV 転送より前（Prefill の開始時）にスケジューラが予約する。
- ステップ送りモードでは、Prefill 完了後にまとめて転送する 1 ステップとして描く（概念を明快に見せるため）。
- 自動再生モードでは、Mooncake 方式などの実態に合わせ、Prefill が 1 層を計算し終えるたびにその層の KV を送り始め、転送を Prefill の計算と重ねて描く。Decode は、全層の KV と最初のトークンが届いた時点で開始する。
- KV-aware routing（すでに KV やプレフィックスを持つ GPU にリクエストを寄せる仕組み）は範囲外とし、スケジューラのステップのツールチップで触れるにとどめる。

画面に明記すること:

- MTP（DeepSeek-V3 の Multi-Token Prediction による投機的デコード）は扱わず、通常の 1 トークンずつの生成として描く。
- マイクロバッチ 2 個のピンポンは「通信を計算と重ねる例」であり、最適な数でも、通信を完全に隠せることの保証でもない。

理由: 分離の利点は「フェーズごとに資源を分けて並行に回せること」なので、重ねて流す表示は外せない。代表の 1 層だけを往復してトークンが出るように見える誤解は、全層の完了と出力 head のステップを分けることで防ぐ。

### 8. 数値の扱い

**常に表示する値**（具体的な経路から導く値）:

- 各フローの経路（ホップ列）
- **Scale-out スイッチの通過数**（例: 1 または 3）。NVLink 中継の回数は別に表示する。「ホップ数」という語は使わない（リンク数や NVLink を含むかどうかが曖昧になるため）。
- Spine を通るデータ量
- リンク負荷（§18）

「1 スイッチで済む」のは、本図では各レールが 1 台の Leaf に収まっているためであり、レール最適化一般の性質ではないことを注記する（大規模構成では同じレールが複数の Leaf にまたがり、Spine を通る場合がある）。

**概算として表示する値**（DeepSeek-V3 の公開 config に基づく。「概算・オーダー感」と明記）:

- **KV Cache 量**: `トークン数 × 61 層 × (512 + 64) × バイト数`。512 は圧縮 KV（latent）、64 は RoPE key の次元。BF16 を基準とし、70,272 バイト／トークン（約 68.6 KiB）。論理的な KV 量と実際の転送量（ページングの余白などを含む）は区別し、表示するのは論理量とする。
- **activation の量**: 「1 トークン・1 MoE 層・片方向」を単位とし、`7168 × バイト数` に送り先の GPU 数を掛ける。同じ GPU 上の複数の Expert へ送る分は 1 回にまとめる。返送も、F 側で GPU ごとに部分和を取るため（§17）、送り先の GPU 1 台につき 1 本となる。「Expert を 8 個選ぶ」ことは「ネットワーク送信が必ず 8 回」を意味しない。
- **精度は方向ごとに定める**: 送る側（dispatch、A→F）は FP8 で 1 バイト／要素、返す側（combine、F→A）は BF16 で 2 バイト／要素（DeepEP の標準的な設定）。量子化の scale やメタデータは含めない概算とする。
- NVLink 中継を行う場合は、ノード単位の重複排除を反映する。Prefill の dispatch では、宛先ノードごとに RDMA で 1 回だけ送り、受信ノード内で NVLink を使って複数の GPU へ配る。combine では、Expert 側のノード内で NVLink を使って集約してから、RDMA で 1 回だけ返す。ネットワーク上の量（RDMA）とノード内の量（NVLink）は分けて表示する。
- 層数は、dense 層 3 層（A↔F や dispatch の通信なし）と MoE 層 58 層に分けて数える。
- AF の A→F / F→A と、EP の dispatch / combine を重ねて数えない（AF 分離時は前者が後者に置き換わるため）。

**表示しない値**: 実時間のレイテンシ、スループットの絶対値。

理由: レール比較はスイッチ通過数と Spine を通るデータ量で十分に伝わる。時間を出すと帯域の前提に議論が逸れ、数字が独り歩きする。

### 9. 入力プロンプト

- テキスト欄にプロンプトを入力できる。ブラウザ内の簡易推定（日本語 1 文字 ≒ 1 トークン、英語 4 文字 ≒ 1 トークン）でトークン数を出し、Prefill 量・KV 量・activation 量の概算に反映する。出力トークン数は別の欄で指定する。
- 入力テキストがトークン（模式的な区切り）に分かれて Prefill 側へ一括で入る様子、Decode で出力トークンが 1 つずつ出る様子を文字で見せる。出力文はダミー（本物の生成ではない）。
- プリセットのプロンプト（短い質問、長い文書の要約など）をワンクリックで切り替えられる。
- 正確な tokenizer は同梱しない（重いため）。「模式的」と明記する。
- 本物の LLM には接続しない。推論サーバへの依存で社外・オフラインの説明に使えなくなり、生成速度とアニメーション速度も合わないため。

### 10. 表示言語: 日英切り替え

- ラベル（Prefill、Decode、Leaf、Spine、dispatch、combine、KV Cache など）は英語で共通。
- 説明文のみ日本語 / 英語を切り替える。文言はステップ定義のデータに日英両方を持たせる。

### 11. 画面レイアウト: トポロジ中央＋右パネル（16:9）

```

│ [PD][AF][Rail-opt]  Prompt:[____▼]  日/EN  ☀/☾ ⚙│
├────────────────────────────────┬─────────────┤
│  Spine ×4                      │ Step n/9    │
│  Leaf ×8 (rail) / ×4 (ToR)     │ 説明文       │
│  Node0  Node1  Node2  Node3    │ スイッチ通過 │
│  (8 GPU each, role label)      │ Spine 経由量 │
├────────────────────────────────┴─────────────┤

```

- レール有無の比較は左右分割にせず、トグル切り替え時に経路が描き直される動きで見せる。
- ⚙ の詳細設定には、「Decode も NVLink 中継する」の ON / OFF（§12）とハッシュの再抽選（§13）を置く。

### 12. 転送方式と NVLink 中継

通信の**目的**（KV / dispatch / combine / A→F / F→A）と**転送方式**（direct / NVLink 中継）を別の属性として扱う。PXN は通信の種類ではなく、転送方式の一つである。

レールをまたぐノード間通信（例: ノード 0 の GPU 0 → ノード 2 の GPU 5）には、次の 3 通りがある。

1. **direct**: 自分の NIC から送る。レール最適化ありなら Leaf0 → Spine → Leaf5 の 3 スイッチを通る。
2. **送信側で NVLink 中継**（NCCL の PXN）: ノード内で GPU 5 へ NVLink で寄せ、NIC5 から送る。Leaf5 だけを通る。
3. **受信側で NVLink 中継**（DeepEP の Normal モードの dispatch）: 宛先ノードの同じレールの GPU 0 へ RDMA で送り、受信ノード内で NVLink を使って GPU 5 へ配る。Leaf0 だけを通る。NCCL でも受信側 PXN がロードマップに載っている。

DeepEP の Normal モードでは、dispatch と combine で経路の規則が逆向きになる。

- **dispatch**: 送信 GPU →（RDMA、送信 GPU のレール）→ 宛先ノードの同じレールの GPU →（NVLink）→ Expert を持つ GPU
- **combine**: Expert を持つ GPU →（NVLink で、元の Attention GPU と同じレールの GPU に集約）→（RDMA、そのレール）→ 元の Attention GPU

いずれも、ネットワーク部分は元の Attention GPU のレールに収まる。

| 通信 | 既定の転送方式 | 根拠 |
| :--- | :--- | :--- |
| Prefill の dispatch / combine | NVLink 中継（DeepEP Normal モード。dispatch は受信側で配り、combine は送信側で集約する） | スループット重視。ツールチップで「NCCL の PXN は送信側で中継する」と補足する |
| Decode の dispatch / combine、A→F / F→A | direct（DeepEP Low-Latency モード）。ノード間は RDMA で直接、ノード内は NVLink で直接 | レイテンシ重視。中継の段数を減らすため、宛先の GPU へ直接送る |
| KV 転送 | direct（NIXL などの RDMA 1 対 1） | NCCL の集団通信ではないため |

- 説明の軸: 「Prefill はスループット重視で中継し、Decode はレイテンシ重視で直接送る。そのため Decode では、レール最適化ありでもレールをまたぐ通信が Spine を通り、Spine の設計が効く」というトレードオフとして見せる。
- 詳細設定の「Decode も NVLink 中継する」を ON にすると、Decode の dispatch / combine と A↔F も中継に切り替わり、Spine を通るデータ量が減る様子（とその代わりに NVLink の中継段が増えること）を見せられる。既定は OFF（実装の実態どおり）。
- レール最適化なし（ToR 型）では、ノード間の通信は中継の有無にかかわらず Spine を通る。**Spine を避けられるのは、本図のレール構成の場合に限る。** ただし ToR 型でも、NVLink 中継によるノード単位の重複排除で、RDMA の量（Spine を通るデータ量）は減る。この 2 つの効果（Spine を避けること、量を減らすこと）を区別して見せる。
- 根拠: DeepEP は Prefill / 学習向けの Normal モード（NVLink 階層集約 ＋ RDMA）と、Decode 向けの Low-Latency モード（宛先への直接送信。ノード内は NVLink も使う）を持つ。参照する DeepEP の版は README に記載して固定する。
- 主トグルにしない理由: PD・AF・Rail-opt と並べると組み合わせが 16 通りになり、説明が散らかるため。

### 13. ECMP のモデル

- **前提**: RoCEv2、フローごとの静的な ECMP、adaptive routing なし。画面の注記にもこの前提を書く。
- **ハッシュの入力**: 送信 NIC の IP、受信 NIC の IP、UDP の送信元ポート（RoCEv2 で QP ごとに決まる値を模擬）。NVLink 中継を行う場合は、論理的な送信元 GPU ではなく、**実際に送信する NIC** の値を使う。
- **フローの単位**: QP（コネクション）ごと。1 つの QP の経路は、ステップをまたいでも変えない。
- **QP の数**: NIC の組ごと、通信の目的ごとに 1 本。これは説明用の仮定であり、実装では複数の QP を使うことが多い。
- **ECMP で決める箇所**: 送信 Leaf での uplink の選択（どの Spine へ、ToR 型では 2 本のどちらで）と、Spine での宛先 Leaf への出力リンクの選択（ToR 型では 2 本のどちらで）の両方を、同じハッシュから決める。
- **ハッシュ関数**: 固定のシード値を使い、毎回同じ結果にする。
- 詳細設定の「ハッシュの再抽選」でシード値を変えられる。押すたびに偏りの出方が変わり、「偏りはトポロジの必然ではなく、ハッシュの当たり外れで生じる」ことを示す。「ToR なら必ず偏る」と受け取られる説明はしない。

### 14. 配色: ライト / ダーク両対応

- OS 設定に追従し、画面上のボタンでも切り替えられる。色は CSS 変数（トークン）で定義する。
- フェーズ（Prefill / Decode / Attention / Expert）、通信の目的（KV / dispatch・combine / A↔F）、転送方式（direct / NVLink 中継）、リンク負荷の色を両テーマで判別できるよう揃える。
- 色覚多様性に配慮し、通信の目的は線種（実線 / 破線など）でも区別する。

### 15. 検証

経路計算とステップ生成を Vitest でテストする。全 16 通り（PD × AF × レール有無 × Decode の NVLink 中継）を対象とし、ホップ数のような結論を前提として固定するのではなく、**具体的な経路が正しく、その結果としての値が導かれること**を検査する。

- **経路の健全性**: すべての経路は、トポロジ上で実際に接続されたリンクだけを通る。
- **MoE の到達性**: 各トークンについて、router が選んだ Expert を持つ GPU すべてにデータが届き、結果が元の Attention GPU に戻る。同じ GPU への送信と返送は 1 回にまとめられている。
- **往復の経路**: Normal モードの dispatch と combine が、§12 のそれぞれの規則（dispatch は受信側で配る、combine は送信側で集約する）どおりの具体的な経路を通る。
- **KV の到達性**: Prefill を担当した GPU の KV が、スケジューラが選んだ Decode GPU に届く。
- **演算の担当**: §17 の担当表どおりに、各演算が A 側 / F 側（または同じ GPU 群）に割り当てられている。dense 層 3 層では A↔F や dispatch が発生しない。
- **転送方式の割り当て**: Prefill の dispatch / combine は NVLink 中継、Decode の dispatch / combine と A↔F は既定で direct、KV は常に direct になっている。
- **スイッチ通過数**: 経路から数えた結果として検証する。例として、レール最適化あり・同じレールの KV 転送は 1、レール最適化なしのノード間通信は 3、レール最適化ありで、レールをまたぐ Prefill の dispatch は 1（NVLink 中継 1 回）、レールをまたぐ Decode の A→F は既定で 3、「Decode も NVLink 中継する」を ON にすると 1。
- **データ量**: KV の量が §8 の式どおりで、プロンプト長に比例する。activation の量が送り先の GPU 数（まとめた後）に比例する。A↔F と dispatch / combine を重ねて数えていない。
- **ECMP**: 同じシード値なら Spine の選択が同じになる。同じ QP の経路がステップをまたいで変わらない。ハッシュには実際に送信する NIC の値が使われている。
- **比較条件**: レール有無の両方で、NIC 数・uplink の合計本数・Spine のポート数が同じである（§18）。
- **ワークロードの固定**: レール有無と「Decode も NVLink 中継する」を切り替えても、リクエスト・Expert の選択・Decode 先が変わらない（§7）。
- **データ量の精度**: 送る側は 1 バイト／要素、返す側は 2 バイト／要素で数えている。NVLink 中継時は RDMA の量がノード単位で重複排除されている。

描画は目視で確認する（スクリーンショット比較は、アニメーション途中の状態が不安定なため行わない）。実装は各タスク完了ごとに Codex レビュー → 指摘の反映 → 次のタスク、の順で進める。

### 17. AF 分離での演算の担当と F への送り方

| 演算 | 担当 | 理由 |
| :--- | :--- | :--- |
| Attention ＋ KV Cache | A | AF 分離の定義そのもの |
| router（top-8 選択） | A | 送り先を決めるのは送る側。A が router を持てば、Expert を持つ GPU へ直接送れる |
| shared expert | A | 全トークンが必ず通る小さな FFN なので、ネットワーク越しに送る意味がない |
| 先頭 3 層の dense FFN | A | 同上。この 3 層では A↔F の通信が発生しない |
| routed experts（256 個） | F | F 側の GPU に均等に配置（EP） |
| 重み付き合算 | F で GPU ごとの部分和、A で最終合算 | A は router の重みもトークンと一緒に送る。F は、その GPU 上の選ばれた Expert の出力を重み付きで足し合わせ、1 本にまとめて返す（DeepEP の combine と同じ考え方）。A は各 F GPU からの部分和と shared expert の出力を足し合わせる |
| residual | A | |
| 出力 head ＋ sampling | A | |

- **F への送り方**: A が router で選んだ Expert を持つ F GPU（最大 8 台。同じ GPU に複数の Expert があれば 1 回にまとめる）へ**直接**送る。送り先の F GPU はトークンごとに変わり、レールもばらばらになるため、レールをまたぐ通信が自然に発生する。転送方式は §12 に従う。
- 業界の AFD は、F 側を別種のチップにする構成が中心である（NVIDIA の Rubin GPU ＋ Groq LPX、d-Matrix と GPU の組み合わせなど）。本ページでは比較を単純にするため F 側も同じ GPU とし、ツールチップと説明文で「F 側を別種のチップにする構成もある」ことに触れる。
- 同じ番号の F GPU を入口にして F 側で配り直す方式は、A→F の既定としては採らない（「Decode も NVLink 中継する」を ON にした場合と、Prefill の Normal モードの dispatch は、この形の中継になる）。ネットワーク部分が 1 スイッチに見えて誤解を生み、実際の方式とも合わないため。
- 非 AF モード（統合型・PD 分離）では、この表の A と F の両方を同じ GPU 群が担当し、routed experts への送信は EP の dispatch / combine になる。つまり、AF 分離と非 AF モードの違いは「送り先が専用の F 群か、同じ GPU 群か」だけであり、比較の説明もしやすい。

### 18. Leaf-Spine の容量と比較条件

両方とも 1:1 のノンブロッキング（oversubscription なし）とし、NIC 数・uplink の合計本数・Spine のポート数を揃える。全リンクの帯域は同じ（単位帯域 1）とする。

| | レール最適化あり | レール最適化なし（ToR） |
| :--- | :--- | :--- |
| Leaf | 8 台 | 4 台 |
| Leaf の downlink | 4 本（各ノードの同じ番号の NIC） | 8 本（1 ノードの 8 NIC） |
| Leaf の uplink | 4 本（各 Spine へ 1 本） | 8 本（各 Spine へ 2 本） |
| Spine | 4 台 × 8 ポート | 4 台 × 8 ポート |
| uplink の合計 | 32 本 | 32 本 |
| ECMP の候補 | 4 本 | 8 本（Spine 4 台 × 2 本） |

- 総帯域も Spine の構成も同じで、違うのは「NIC をどの Leaf に配線するか」だけになる。Leaf の台数の違いは、配線方法による結果として説明する。
- **リンク負荷**: ステップごとに各リンクを通るデータ量（概算バイト数）÷ リンク帯域を、相対値の色で示す。表示名は「リンク負荷（このステップの転送量、模式）」とし、「混雑」とは呼ばない。描画速度に左右される「同時に流れているフロー数」は指標にしない。
- 1:1 のノンブロッキングでも、静的な ECMP ではハッシュの衝突でリンクが偏ることがあり、競合がないことは保証されない。
- 比較の結論は「Spine を通るデータ量」と「スイッチの通過数」に限定し、性能の優劣は断定しない。Spine を通るデータ量が増えることと、実際に混雑することは同じではないため。

### 19. GPU の世代と精度

- GPU の世代は特定せずに描く。特定の製品名を前面に出すと、GPU の世代比較の議論に引っ張られるため。
- 画面の注記で次の 2 点を示す。
  - 本図は DeepSeek-V3 の構造と寸法を参考にした通信の例であり、この 32 GPU 配置でモデルが収まることは保証しない。
  - ただし、V3 はもともと FP8 で公開されたモデルであり、FP8 なら routed experts は約 0.65 TB と、H200 / B200 世代の 8 GPU に収まる規模である（PD＋AF で Decode-F を 1 ノードにまとめる配置も、ありえない構成ではない）。
- データ量の概算は、送る側の activation を FP8、返す側を BF16、KV を BF16 で計算する（§8。KV は公式の推論実装で BF16 が一般的なため）。

### 20. DeepSeek-V3 のノード制限ルーティング

- DeepSeek-V3 は、1 トークンの送り先を最大 4 ノードに制限している（node-limited routing。ノード間の通信量を抑えるため）。
- 本図の構成では、Expert を持つノードは最大 4 ノード（統合型）なので、この制限は実質的に効かない。router の選択はこの制限を満たす形で生成し、ツールチップで制限の存在に触れる。
- 実際の config にある group-limited routing（256 Expert を 8 グループに分け、そのうち 4 グループから選ぶ）は再現しない。この省略も注記する。

### 21. Scale-up のみの構成（軽量モデル）

「軽量なモデルなら Scale-up だけで足りる」ことを示すため、ネットワークの切り替え（**Scale-up のみ** / **Scale-up + Scale-out**）を追加する。

- **基準モデル**: Scale-up のみでは、Qwen3-30B-A3B 相当の軽量 MoE に切り替える（公開 config: hidden 2048、48 層（すべて MoE、dense 層なし）、routed expert 128 個中 8 個、shared expert なし、GQA の KV 4 ヘッド × 128 次元）。KV は BF16 で `48 × 2（K, V）× 4 × 128 × 2 B = 98,304 B／トークン`、送信は 2048 × 1 B（FP8）、返送は 2048 × 2 B（BF16）とする。説明文の層数や shared expert の有無も、モデルに合わせて切り替える。
- **配置**: 重みは BF16 でも約 61 GB で 1 ノードに十分収まるため、4 ノードはそれぞれ独立したレプリカ（ノード間は DP、通信なし）として動かす。各ノードは Expert 一式を持ち、8 GPU に 16 個ずつ均等に置く（ノード内 EP8）。Attention は §5 と同じ DP attention。
- **PD / AF / 配線**: Scale-up のみでは統合型だけを表示し、PD 分離・AF 分離・レール最適化と詳細設定（Decode の中継、ECMP の再抽選）は無効にする。ノード内での PD / AF 分離は扱わない（分離はノード間の資源分割として説明する方が主題に合うため）。
- **見せ方**: Leaf-Spine は消さずに薄く表示し、「存在するが使われない」ことを Scale-out ありとの切り替えで一目で比べられるようにする。dense 層のステップと KV 転送のステップは発生しないので表示しない。
- **ワークロード**: リクエストの長さと router の選択は §7 と同じ生成規則で、Expert 数と top-k だけをモデルに合わせる。

### 22. GPU 内部の表示（代表 GPU のカード）

32 GPU すべての内部は描けないため、役割ごとに代表 GPU を 1 台ずつ選び、トポロジのノードの下にカードとして並べる。

- **代表の選び方**: 追跡中のリクエストが通る GPU を代表にする。統合型（Scale-up のみを含む）は U の 1 枚、PD 分離は P と D、AF 分離は A と F、PD＋AF は P と D-A と D-F。F は、追跡中のリクエストの最初の Decode トークンが選ぶ最初の Expert を持つ GPU とする（シナリオ内では固定）。カードからトポロジ上の GPU へ点線を引く。
- **処理ブロック**: Embed → Attention → KV Cache →（dense FFN）→ Router → Experts → Combine + residual → Head を並べ、現在の段階で動いているブロックを点灯する。A 側は Experts の代わりに Send / Recv、F 側は Recv → Experts → Send だけを描く。dense 層のないモデルでは dense ブロックを描かない。
- **Expert の一覧**: その GPU が持つ routed expert をマスで並べ、追跡中のリクエストが選んだものを点灯する（Prefill はプロンプトの先頭 64 トークンまでの和集合、Decode は現在のトークン）。P は常に Prefill の配置で数える。
- **層の進み具合**: 「層 1–3 / 61（dense）」「代表 MoE 層（4–61 層目）」「61 / 61 層 → 出力 head」のように示す。
- **HBM の内訳**: 重み・KV・activation を積み上げバーで示す。GPU の世代を特定しない方針（§19）のため容量は出さず、このシナリオ内の最大を 100% とする相対表示とし、各値は概算として数値も添える。重みは公開されているパラメータ数から、routed expert とそれ以外（attention、shared expert、dense FFN、embedding）に分けて見積もる（DeepSeek-V3: FP8、約 671B、Qwen3-30B-A3B: BF16、約 30.5B）。Attention 側はそれ以外の重みを、Expert を持つ GPU はその割合の Expert の重みを持つ。KV は、その GPU が担当するリクエストについて、Prefill の進み具合（dense 後 3/61、代表 MoE 層で 1/2、完了で全量）と、KV 転送後は Decode 側へ移ること（P からは解放）、Decode で生成トークン分だけ増えることを反映する。
- **並行動作モード**: カードも表示し、P と D、A と F が同時に点灯する様子を見せる。KV の値は代表的な途中状態の概算とする。

### 23. ブロックの拡大表示（MoE 層の中身）

Transformer Explainer のようなモデル内部の可視化は、主題（GPU 間とネットワークの流れ）から外れ、§9 の「本物の LLM に接続しない」方針とも合わないため、同じものは作らない。代わりに、このページならではの MoE の話に絞った模式的な拡大表示を加える。

- GPU カードの処理ブロックをクリック（または Enter / Space）すると、右パネルにそのブロックの中身を表示する（§12 のピン留めと同じ操作、Esc で解除）。
- **Router**: 追跡中のトークンの top-k の Expert と重み（大きい順）、各 Expert がどの GPU にあるか（この GPU / 同じノード / 別ノード）。
- **Experts**: この GPU で計算する Expert ごとに FFN の形（`x [hidden] → gate / up [moe_intermediate] → SiLU ⊙ → down [hidden] × 重み`）。
- **Combine**: Expert を持つ GPU ごとの部分和と重みの合計、shared expert（あれば）、residual。
- **Attention / KV**: MLA（latent 512 ＋ RoPE key 64）と GQA（Query 32 ヘッド、KV 4 ヘッド × 128）の違い、文脈の長さ、1 層と全層で読む KV の量（Decode がメモリ帯域に縛られる理由）。
- その他（Embed、Dense、Head、Send、Recv）は短い説明のみ。
- 対象のトークンは、カードと同じ規則で決める（P は Prefill、ほかは現在のフェーズ。PD 分離時の Prefill 中は、Decode 側のカードは対象なし）。数値は公開 config と決定的なワークロードから出し、「模式図であり実モデルは動かしていない」と明記する。
- モデル仕様に `expertInter`（DeepSeek-V3: 2048、Qwen3-30B-A3B: 768）と Attention 方式を追加する。

## Consequences

- 経路がデータから計算されるため、レール有無や割り当ての変更がコード全体に波及しない。一方で、トポロジ・演算の担当・経路・ステップのデータモデルを最初に丁寧に設計する必要がある。
- 通信の目的と転送方式を分けたため、NVLink 中継のような転送方式を後から追加・変更しやすい。
- 時間や性能の数値を出さないため、「どれくらい速くなるか」という問いには答えないページになる。必要なら別ページやスライドで補う。
- 表示規模を 32 GPU に縮め、並列化も DeepSeek-V3 の実運用とは異なる模式配置としているため、実際の大規模クラスタ（数千 GPU、多段 Spine）とは規模感が異なる。説明パネルで「縮小した模式図」であることを明記する。
- 出力文はダミー、トークン分割は模式的、データ量は概算、ECMP の偏りはハッシュの一例であることを、画面上で常に分かるようにしておく必要がある。
